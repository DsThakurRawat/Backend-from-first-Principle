AI Agents & Loop Engineering

Part IV / OpenAPI & AI Agents · Companion notes for src/content/chapters/26-ai-agents-and-loop-engineering.mdx

The core idea

An LLM call returns text. An AI agent is a bounded backend workflow that observes state, chooses an action, calls an allowlisted tool, observes the result, and either continues or stops. The model proposes a transition; the backend owns authorization, state, limits, and side effects.

Do not give the model a database connection.Expose narrow tools such as get_order(order_id). Validate arguments and tenant scope in backend code, and require approval before irreversible actions.

Loop Engineering

Engineer the loop as a state machine:

  1. Inspect: load identity, request state, tools, budget, and deadline.
  2. Plan: let the model propose a tool call or final response.
  3. Act: validate and execute one allowlisted capability.
  4. Observe: append a bounded, structured result.
  5. Evaluate: check evidence, completion, policy, and remaining budget.
  6. Stop: return success, typed failure, or an approval request.

LangGraph skeleton

from typing import Annotated, Literal
from typing_extensions import TypedDict
from langchain_core.messages import AnyMessage, HumanMessage, ToolMessage
from langchain_core.tools import tool
from langchain_openai import ChatOpenAI
from langgraph.graph import END, START, StateGraph
from langgraph.graph.message import add_messages

class AgentState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    steps: int

@tool
def get_order(order_id: str) -> dict:
    """Read an order visible to the authenticated tenant."""
    return {"order_id": order_id, "status": "shipped"}

model = ChatOpenAI(model="gpt-4.1-mini", temperature=0).bind_tools([get_order])

def call_model(state):
    response = model.invoke(state["messages"])
    return {"messages": [response], "steps": state["steps"] + 1}

def run_tools(state):
    last = state["messages"][-1]
    return {"messages": [ToolMessage(content=str(get_order.invoke(call["args"])), tool_call_id=call["id"])
                          for call in last.tool_calls]}

def route(state) -> Literal["tools", "done", "failed", "limit_reached"]:
    last = state["messages"][-1]
    if getattr(last, "tool_calls", None) and state["steps"] < 4:
        return "tools"
    if getattr(last, "tool_calls", None):
        return "limit_reached"
    return "done" if str(getattr(last, "content", "")).strip() else "failed"

graph = StateGraph(AgentState)
graph.add_node("model", call_model)
graph.add_node("tools", run_tools)
graph.add_node("failed", lambda state: {"status": "failed", "error": "empty model response"})
graph.add_node("limit_reached", lambda state: {"status": "limit_reached", "error": "agent step limit exceeded"})
graph.add_edge(START, "model")
graph.add_conditional_edges("model", route, {"tools": "tools", "done": END, "failed": "failed", "limit_reached": "limit_reached"})
graph.add_edge("tools", "model")
graph.add_edge("failed", END)
graph.add_edge("limit_reached", END)
agent = graph.compile()

Backend integration

Keep the HTTP handler ordinary: authenticate the user, create an idempotent run, enqueue work, and return 202 Accepted. A worker executes the graph with a deadline and checkpoint. Store the run status, step count, tool calls, usage, errors, and timestamps. Never let the model decide tenant scope or authorization.

@router.post("/agent-runs", status_code=202)
async def create_agent_run(request, user=Depends(current_user)):
    run = await runs.create_if_absent(
        user_id=user.id,
        tenant_id=user.tenant_id,
        idempotency_key=request.idempotency_key,
        prompt=request.prompt,
    )
    await queue.publish("agent.run.requested", {"run_id": run.id})
    return {"run_id": run.id, "status": run.status}
Replacement rule

Use a fixed workflow when the sequence is known. Use an agent when the next step genuinely depends on evidence. Use a hybrid when only one decision point needs dynamic routing.

Production checklist

  • Bound model calls, tool calls, tokens, and wall-clock time.
  • Validate tool inputs and outputs with typed schemas.
  • Use idempotency keys for mutations and approvals for irreversible actions.
  • Treat retrieved content as untrusted data to reduce prompt-injection risk.
  • Trace latency, cost, tool failures, retries, and final outcomes.
  • Test wrong arguments, missing data, timeouts, adversarial content, and resume-after-crash behavior.
